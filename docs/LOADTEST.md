# 부하 측정 (동시 사용자 한도)

측정일 2026-10-06. 코드와 서버 설정은 바꾸지 않았다(vlm/paddle 재시작·변경 없음). 추가한 것은 `tools/load/`뿐이다.

## 측정 조건

- 서버 elgrim: EPYC 7642 48코어(논리 48), 251GB. vlm(Qwen3-VL-32B, `--parallel 1`, A4000+TITAN Xp), paddle(PaddleOCR-VL-1.6, `--parallel 4`, A4000).
- 하네스 `tools/load/load.py`: 컨테이너 1개 안에서 `ProcessPoolExecutor(N, fork)`로 `convert.convert(..., no_upload=True)`를 N개 동시 실행. N명이 응답 즉시 다음 요청을 보내는 닫힌 루프(요청 수 N×3 이상). 프로세스를 쓴 이유: `ocr.ACTIVE`/`STATS`가 프로세스 전역이라 스레드로 섞어 돌리면 auto 폴백 판정이 서로 덮어쓴다.
- 지연은 한 요청의 convert 시작~끝(업로드 제외). 모니터 `tools/load/mon.py`가 1초마다 CPU%, loadavg, nvidia-smi, `/slots`(paddle/vlm 점유 슬롯 수)를 기록. 컨테이너 기동(`python -c`)은 0.20~0.24초(3회).
- 입력: A는 사진 7장 + `activity_09_300dpi.png` 8개를 순환. B는 `scan_attendance_09.pdf`(단독 54초)와 `scan_meal_09.pdf`(단독 11초). D는 디지털 PDF 3개(activity/attendance/meal).
- 정확도: 근무일정표(sched_09~12) 칸 내용을 `score.content_score`로 채점.

## 측정 한계

- 닫힌 루프(N명이 쉼 없이 요청)이다. 실제 도착은 랜덤이므로 같은 평균 부하에서 꼬리 지연은 더 커질 수 있고, 동시 사용자 수는 "동시에 처리 중인 요청 수"에 해당한다.
- 입력은 사진 8개 순환(칸 수 약 52개/장 평균, 큰 사진 변동 미반영), 스캔은 2개 파일, B4는 1회, C는 1회, E는 구간당 1회라 반복 오차를 못 잡았다.
- 한 컨테이너의 프로세스 풀로 측정했다. 실제 서비스 구조(웹서버, 업로드 대기열, 사진 파일 수신 시간, 이미지 크기 제한)는 포함하지 않았다. 프로세스마다 OpenCV 스레드 기본값이라 CPU 오버섭스크립션이 있을 수 있다(CPU는 병목이 아니어서 영향은 작다).
- A~D는 업로드를 끄고 측정했고, 종단(변환+업로드) 동시 부하는 측정하지 않았다(F의 합산은 추정).
- CPU 사용률은 1초 샘플이라 짧은 최대치를 놓칠 수 있다. 업로드는 한 계정, 28개 생성이라 일일 한도 근처 동작과 12 이상 동시 요청 시 한도 에러 형태는 모른다.
- 24시간 포화 가정의 일당 수치는 이론 상한이다(발열, 장시간 안정성은 측정 안 함).
