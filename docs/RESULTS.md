## 개선 이력

- 1라운드: 표 이미지/PDF -> TableSpec. 전처리, 격자, 벡터, 서식, OCR, Apps Script 작성기, 합성 데이터 채점, 표 기준 원근 보정, 셀 단위 OCR.
- 2라운드: 페이지 전체 재현(PageSpec v2). PDF 경로(pdfvec, layout, verify)와 사진 경로(photopage, ocr, style, verify_photo)를 따로 구현. 표 전체 1회 OCR + 행/이웃 재질의, 조명 평탄화/배경 판정, 표 밖 텍스트 블록, 내용 채점, 시트 교체 도구.
- 3라운드: 두 경로를 `convert` 한 진입점으로 연결(자동 판별, 스캔 PDF 경로 추가, 검증 라우팅). 결함 a~f 수정, 굵기 일치율 지표 추가, Apps Script `list` 액션으로 고아 시트 정리(38개 -> 10개), 업로드 재시도, 문서화.

## 속도 개선 (4라운드)

변경: (1) `convert` 기본은 스펙 생성 + 시트 업로드(create 1회)까지만 하고 URL을 반환한다. 시트 PDF 내보내기, 겹쳐 채점, 정답 채점은 `--verify`일 때만 한다. (2) vlm 출력을 JSON에서 압축 텍스트로 바꿨다. 표 전체 호출은 CV가 잉크 있다고 본 칸만 요청하고 완전히 빈 행은 요청하지 않으며, 출력은 한 줄에 한 행 `행번호|칸|칸` 이다. 행 단위 읽기, 이웃 칸 재질의, 표 밖 글줄 읽기도 같은 원칙(요청한 칸만, 따옴표/키/괄호 없음)이다. (3) llama.cpp `grammar`(GBNF) 파라미터가 이 서버에서 동작함을 확인했고(`/v1/chat/completions` 본문에 `grammar` 전달), 줄 수, 줄마다 `|` 개수, 행번호를 문법으로 강제한다. 문법이 막아 주므로 칸 밀림은 구조적으로 생기지 않으며, 코드에서도 개수를 한 번 더 검증해 어긋난 행은 기존 행 재질의로 넘긴다(측정 중 어긋난 행 0). (4) 프롬프트를 줄였다(열 너비 비율은 유지, 병합 설명은 요청 칸 목록으로 대체). 이미지 해상도는 그대로(긴 변 <= 1900px, 축소 없음).

측정은 검증을 끈 `convert`, 호출 직렬, 시트 `--delete`(sched_09만 `v4_sched_09`로 보존)이다. 시간은 변환 + 업로드 전체(초). 정확도는 같은 spec JSON을 `tools/accuracy.py`로 오프라인 채점했다. 이전 값은 `runs/convert/*/convert.json`(3라운드, 검증 포함)이고 이전 생성 토큰은 vlm 로그로 확인(아래 정정 참고).

- paddle의 실패 양상: 한 글자짜리 칸("월", "요일")에서 뒤에 군더더기를 붙인다("월 1", "월 2", "요일 ___", "요일 ㅅㅇㅇㅇ..."). 패딩을 12~16px 주면 재현되고 패딩 0~3px + 잉크 조임에서는 사라졌으나, mmproj를 CPU에서 돌리거나 패딩을 크게 하면 다시 나온다(수치 경로 의존, 첫 토큰 확률 약 0.5). 숫자/시각/한글 본문은 4장 모두 정확했다.
- 확률 기반 의심 칸 선별은 맞지 않는다. 최소 토큰 확률 <0.95는 칸의 43%(26~27개/장)가 걸리고(공백/표기 차이 때문), 대부분 정답이다. <0.6으로 낮추면 장당 2~6칸이 걸리지만 실제 오답("월 1") 일부는 놓치거나 반대로 32B 이웃 크롭 재질의가 끝에 체크 글자를 붙이거나 설명문을 뱉어("필요한 정보를 정확히 추출하기 위해...") 오히려 틀린다. 즉 32B의 `read_neighbors` 경로가 좁은 칸에서 불안정하다.
- 속도 정정: GTX 1050은 같은 입력을 되풀이하면 장당 6초(llama.cpp 프롬프트 캐시)가 나와 빠르게 보이지만 콜드는 장당 약 50초다. 측정은 입력/패딩을 바꿔 콜드로 확인했다. A4000은 콜드에서도 장당 5초대.
- 공존: 32B가 A4000을 14.4GB 쓰므로 남는 약 1.9GB에 paddle(GPU mmproj)은 `cudaMalloc` OOM(mmproj 841MiB 버퍼). mmproj를 CPU로 돌리면 들어가지만 장당 약 110초로 오히려 느리다. GTX 1050에는 올라가지만 Pascal fp16이 느려 장당 약 50초. 따라서 현재 구성에서 32B와 paddle을 같은 속도로 동시 상주시키는 방법은 못 찾았다. 선택지: (1) paddle 전용으로 A4000을 쓰고 32B는 필요할 때만 켜기(32B는 A4000+TITAN 둘 다 필요), (2) 32B를 계속 쓰고 paddle은 포기, (3) A4000 한 장을 쓸 수 있는 qwen8b(12.3GB)도 32B와 동시 상주 불가.
- 스캔 PDF/빈 양식: 스캔(104칸)은 A4000 paddle로도 장당 86초가 걸렸다(칸이 크고 긴 글을 칸마다 따로 읽음). 빈 양식 3장은 paddle A4000 콜드로 4.7~18초. 이 두 경로는 표 전체 1회 호출이 오히려 유리하다.
- 32B 정지 시간: 07:46~07:56(약 10분). 종료 시 `docker start vlm` 후 healthy 확인, 테스트 컨테이너 모두 제거, A4000 14.47GB / TITAN 11.73GB / 1050 3MB로 원상 복귀.

## 7라운드: 긴 칸 잘림 (2026-10-06)

문제: 글자가 많은 표(`data/pdfs/activity_09.pdf`, 원본 텍스트 940자)에서 답이 조용히 잘렸다. 입력은 사진본 `activity_09_300dpi.png`(auto -> paddle)와 스캔본 `scan_activity_09.pdf`(32B). 채점은 `tools/accuracy.py pdf <spec.json> data/pdfs/activity_09.pdf`(글자 다중집합). 서버 설정 변경 없음(paddle `-c 8192 --parallel 4`, vlm 그대로).

| 입력 | 전: 정확도 / extra / 시간 / 잘림 | 후: 정확도 / extra / 시간(변환 / 전체) / 잘림 |
|---|---|---|
| 활동일지 사진(auto) | 809/940 (86%) / 0 / 28.1초 (변환 5.2) / 감지 없음 | 932/940 (99.1%) / 1 / 14.5~16.9초 (변환 5.2) / 0 |

원인과 처리:

1. 사진본 소실(86%)의 주 원인은 max_tokens 가 아니라 layout 이었다. 두 줄 칸은 줄 간격(3.9mm)이 글줄 잉크 높이(5.2mm, 괄호 포함)보다 좁아 두 블록의 bbox 가 세로로 겹친다. paddle 은 두 줄을 따로 정확히 읽었지만(블록 20개), `layout.build_page_spec` 이 겹친 두 번째 블록을 `block_overlaps_table` 로 버렸다(6개, `(`/`)`/진 등 131자). 처리: `photopage._bands` 가 가로로 겹치는 이웃 글줄과의 중간선으로 블록 세로 범위를 자르고 bbox 도 거기까지만 둔다(기본 사진 `max_tokens=64` 한도는 이 입력에서 실제로 잘리지는 않았다: paddle 최대 생성 44토큰, 최대 프롬프트 193토큰).
2. 잘림 감지/처리(전 호출): paddle `finish_reason=length` -> 한도 2배(최대 512) 1회 재요청 -> 그래도 잘리면 그 칸만 32B(`ocr.paddle_read`, `read_crop32`). 32B 표 호출이 잘리면 `Overflow` 로 행을 나눠(병합 칸을 가르지 않는 경계) 재요청, 한 행이면 한도 2배 1회. 32B 행/줄/이웃 재질의는 2배 1회 재요청. 횟수는 `meta.trunc`(paddle: trunc/retry_ok/to32/max_prompt/max_out, qwen32b: trunc/retry/split/trunc_final)에 기록하고 convert 출력에 `trunc(...)`, `ocr_backend`, `auto_fallback` 로 표시. 강제 시험(`tools/r7_stress.py`): paddle 한도 40 으로 줄이면 7칸이 잘려 7칸을 32B 로 보내고 932/940 유지. 실제 스캔 실행 1회에서 32B 단일 호출이 잘려(120 -> 240) 재요청이 동작했다.
3. 칸별 한도: `ocr.est_tokens`(CV: 행 투영 덩어리 수와 잉크 높이로 글줄 수, 잉크 폭/(0.45 x 글자 높이)로 글자 수, x1.3 토큰 x1.5 여유). paddle 한도 = 추정(64~512), 32B 표 한도 = 40 + 6 x 행 수 + sum(칸 추정+3), 행/줄 한도도 같은 방식. 이전 고정값(표 200+25 x 칸, 줄 120, 행 60+25 x 칸)은 추정이 없을 때만 쓴다.
4. 컨텍스트 보호: `ocr.fits` = 이미지 토큰(`(h/32)x(w/32)+8`) + 프롬프트 글자 수 + 40 + 출력 한도 > 8192 x 0.9 이면 전송 전 `Overflow("too_big")` 로 행을 나눠 보낸다. 실측 대조(스캔 호출 로그): (1663x1004)->프롬프트 1968토큰(식 1672 + 텍스트 약 290), (219x876)->292(식 204 + 88), (151x604)->198(식 103 + 95). 식이 이미지 부분을 정확히 맞히고 텍스트는 글자 수 + 40 으로 덮인다. `CTX=3600` 강제 시험에서 표 호출이 미리 2개로 나뉘고 932/940. paddle 은 프롬프트 최대 193 + 출력 최대 512 라 슬롯당 2048 에 충분해 `-c` 는 그대로 둔다.
5. 32B 엉뚱한 글자 72개: 원인은 형식 문법이었다. `cell ::= [^|\n]{0,80}` 이 `<`/`>`와 이모지를 허용하고, 마지막 줄을 `\n` 으로만 끝낼 수 있어 모델이 종료 토큰 대신 `</tool_call>` 같은 조각(l,o,t,c,a,_,<,>)과 ✅ 를 글자로 써 넣었다(이웃 칸 혼입이 아니라 종료 문법 문제. 두 줄 칸 아래 줄이 "정도 누업 보소" 처럼 깨진 것은 읽기 크롭에 위아래 이웃 글줄이 섞인 것이라 `_bands` 로 크롭도 이웃 중간선에서 자르도록 고쳤다). 처리: 허용 글자에서 `<`, `>`, U+2600-27BF, U+1F000-1FAFF 를 뺐고(원본에 있는 괄호 - / : , . ~ 는 허용), 마지막 줄의 `\n` 을 선택으로 해 종료 토큰이 문법 안에서 나오게 했다. 칸 최대 길이 80 -> 160자(paddle 폴백 조건 `long` 도 같은 값). 이 문법 변경을 하다가 `\n` 을 선택으로 하지 않은 첫 시도에서는 종료를 못 해 칸이 되풀이 생성되어 extra 727이 나왔고(한도까지 생성), 선택으로 바꿔 해결했다.

재현: `tools/run_r7.sh`(컨테이너 안), 맥에서는 `tools/r7_elgrim.sh <접두> [act]`(rsync 후 elgrim nohup, 로그 `runs/<접두>.log`, act 는 활동일지 2건만). 통과선: 사진/스캔 >=931/940 & extra<=5, 근무일정표 290/290, 머리글 18/18, scan_attendance_09 664/664 (모두 통과).

동시 부하: 서버 설정을 바꾸지 않아 재생성은 하지 않았다. 실행 내내 vlm/paddle RestartCount 0, OOMKilled false, A4000 최대 14,997MiB(여유 약 1.4GB).

남은 한계: 활동일지 누락 8자(도, 지, 교, 명 또는 환, 과, /, 내, 용)는 ~~표 바깥 오른쪽 열의 작은 머리글이 버려지는 것~~ (정정: 8라운드. 이는 잘못된 해석이었다. 가장 넓은 마지막 열 "교과 / 지도 내용" 전체가 `trim_outer` 로 표에서 잘려 나갔고, 머리글 8자는 그 열의 머리글 칸이다. 아래 8라운드 참조.) 통과선(931)에는 1자 여유만 있다. 두 줄 칸은 줄 간격이 좁은 만큼 시트에서는 같은 행 높이 안에 겹쳐 놓인다. 32B 칸 한도 추정이 틀려 잘리면 재요청 1회 후 잘린 글자가 그대로 남는다(`trunc_final` 로 보인다). 스캔 시간은 기록만(77~81초, 22호출).

## 9라운드: 서식 정답 채점 (2026-10-06)

문제: 사진/스캔 경로의 서식 추정이 디지털 PDF 정답과 달랐다(활동 일지 사진본을 시트로 만들어 원본과 나란히 본 결과). (1) 마지막 열 "교과 / 지도 내용"이 원본은 전부 왼쪽 정렬인데 시트는 일부 행만 가운데, (2) 머리글 행이 보통이고 "순"/"시간" 열 숫자가 굵게, (3) 머리글 "날짜 / (요일)" 두 줄이 한 줄로.

채점 추가(`score.style_score`, `tools/style_eval.py`, `tools/style_table.sh`): 정답 = 같은 PDF 의 pdf_vector 결과. 정답에서 글자가 있는 표 칸(키 r,c,rs,cs)마다 가로/세로 정렬, 굵기, 칸 안 줄 수(\n 개수 + 1), 글자 크기(+-1pt), 배경 유무(전체 칸), 테두리 4변(전체 칸)을 보고, 표 밖 블록(제목, 작성자 줄, (서명))은 텍스트 유사도 0.7 이상 또는 중심 위치 12mm 이내로 짝지어 굵기/크기/정렬을 본다. 6개 입력 = attendance/activity/meal 사진 PNG(300dpi) + 스캔 PDF.

원인과 수정:

1. 정렬(`photopage.align_pass`, `style.analyze` 에 gl/gr/fill/글줄 띠 x 범위 추가): 기존은 좌우 여백 차이가 칸 폭의 24% 이내면 가운데였다. 86mm 칸에 거의 가득 찬 긴 글은 여백이 비슷해 가운데로 갔다. 이제 문턱은 2mm(칸 폭 5% 중 큰 값). 글줄이 2줄 이상이면 줄 왼쪽 끝이 1mm 안에서 같을 때 왼쪽, 오른쪽 끝이 같으면 오른쪽. 80% 이상 채운 21자 초과 글은 왼쪽. 문턱 1~2배 구간의 애매한 칸만 같은 열(본문)/행(머리글)의 분명한 칸 3개 이상, 60% 이상 다수결을 따른다. 분명한 칸은 열 다수결에 덮이지 않는다.
2. 굵기(`style.hangul_thickness`, `photopage.bold_pass`): 기존 둘레 대비 면적 비율은 글 내용에 좌우됐다(숫자 "1"이 굵게, "09:00"은 얇게, 머리글과 본문이 겹침). 칸을 4배 확대해 한글 음절 크기(가장 큰 덩어리 높이의 70% 이상, 너비/높이 0.75 이상) 덩어리만 거리변환 능선의 중앙값으로 획 두께를 재고 글자 크기(em)로 나눈다(보통 0.047~0.075, 굵게 0.093~0.11; 두 군집 사이 0.08 문턱, 페이지 분포에 0.012em 이상 간격이 뚜렷하면 그 가운데). 숫자만 있는 칸은 글꼴이 달라 두께를 못 쓰므로 같은 행의 한글 칸 다수결을 따른다. 머리글 행은 행 단위 다수결, 본문 한글 칸은 칸마다(합계 행처럼 칸마다 다른 원본이 뭉개지지 않는다).
3. 줄바꿈(`photopage.break_pass`): paddle 은 칸 통째로 읽으면 자동 줄바꿈된 긴 글의 \n 을 주지 않고, 칸 읽기 후처리도 개행을 공백으로 합쳤다. 이미지의 글줄 띠(행 투영, 틈 4px 이상)가 2줄 이상인 칸은 줄마다 크롭을 paddle 로 읽어, 칸 전체 글에서 그 줄 끝에 가장 가까운(편집거리) 자리에 \n 을 넣는다(글자는 칸 전체 읽기 그대로). 명시적 줄바꿈과 폭 때문에 자동 줄바꿈된 줄을 구분하지 않고 이미지의 줄 그대로 둔다. 정답(pdf_vector)도 줄마다 \n 을 넣는 방식이고, 폭에 맡기면 시트 글꼴(나눔고딕)이 달라 줄 수가 틀어진다. 줄바꿈 후 추가 paddle 호출은 칸 줄 수 합(활동 일지 약 12회, 4병렬).
4. 배경: `BG_MIN_DROP` 18 -> 12 (meal 머리글 #efefef 는 종이보다 16 어두움). 근무일정표와 합성 bench 는 변화 없음.
5. 표 밖 블록: 표 오른쪽 끝(14mm 안)까지 가는 마지막 조각이 앞 글과 글줄 높이 1.25배 넘게 떨어져 있으면 따로 읽는다(작성자 줄과 (서명)이 한 블록으로 읽혀 (서명) 정렬이 LEFT 로 나오던 것). 같은 글줄에서 갈라진 조각은 글자 수가 가장 많은 조각의 크기를 같이 쓰고, 마지막 조각은 RIGHT. 도장/손글씨 서명(중앙값 2.2배 초과 덩어리)은 높이 계산에서 뺀다(읽기 범위는 그대로). `layout.pad_blocks`: 서로 마주 보는 두 블록이 원래 좌표 기준으로 각자 늘어나 겹치던 것을 둘 사이 가운데까지만 늘리게 고침(겹치면 한쪽이 block_overlaps_table 로 버려졌다). 표 칸 크기 단계 묶기(`unify_sizes`)를 표 밖 블록과 분리.
6. 시도했다가 되돌린 것: 블록 높이를 윗/아랫 끝 10/90 분위로 재는 방식은 큰 굴림 제목(meal "급 식 확 인 서")의 크기를 맞췄지만 form_attendance 페이지 격자가 24행 -> 23행으로 바뀌어(8라운드 구조 기준 위반) 뺐다. 그래서 표 밖 블록 크기 정확도는 오르지 않았다.

| 표 밖 블록 크기(+-1pt) | 6/20 = 30% | 19/20 = 95% |
| 표 칸 서식 지표(h/v/굵게/줄 수/크기/배경/테두리) | 변화 없음 | 변화 없음 |

남은 1개는 meal 사진의 "(서명)"이 앞 줄과 한 덩어리로 읽혀 짝이 안 되는 경우다.

### 3. 테스트 시트 절감
`tools/run_r10.sh <접두>` 는 시트를 만들지 않고(`convert --no-upload`) 채점한다. `--sheets` 는 대표 2개(v6_activity_photo, v7_sched_09)만 만들고 나머지는 `cleanup.py` 로 지운다. 이번 라운드 시트 생성은 sample_spec 점검 1 + v6 2 + v7 1 = 4개(중복 1개 정리).
